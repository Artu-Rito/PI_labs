# Требования к проекту Furniture Management System

Версия документа: 1.0

## 1. О приложении

Furniture Management System (FMS) - backend для мебельной компании. Нужен, чтобы обрабатывать заказы готовой мебели из каталога и заявки на мебель по индивидуальным параметрам.

Сейчас (на момент ЛР2) в приложении реализован только один эндпоинт - `GET /health`, он просто проверяет что сервис запущен. Каталога, заказов, заявок и ролей пока нет, всё это описано ниже как требования на семестр.

Роли:
- Клиент - смотрит каталог, оформляет заказы готовой мебели, оставляет заявки на индивидуальное изготовление, смотрит статус своих заказов.
- Менеджер - смотрит заказы и заявки, которые пришли, уточняет параметры индивидуального заказа, считает стоимость, меняет статус заказа.

Термины:
- Товар - позиция в каталоге готовой мебели (название, цена, сколько в наличии).
- Заказ - когда клиент покупает один или несколько товаров, либо когда заявка подтверждена менеджером и превращается в заказ.
- Заявка (custom request) - клиент присылает параметры мебели, которую хочет сделать на заказ, до того как менеджер её подтвердит.
- Статус заказа - в каком состоянии сейчас заказ (новый, в работе, готов, выполнен, отменён).

## 2. Требования к функционалу

| № | Требование | Приоритет | Состояние | Признак выполнения |
|---|---|---|---|---|
| FR-1 | Пользователь может проверить, что API вообще работает | Обязательно | Уже есть | GET /health отвечает {"status": "ok"}, код 200 |
| FR-2 | Клиент может зарегистрироваться и войти в систему | Обязательно | Нужно сделать | После регистрации и входа клиент получает токен и может делать запросы от своего имени |
| FR-3 | Клиент может посмотреть каталог мебели | Обязательно | Нужно сделать | GET /products отдаёт список товаров с названием, ценой и остатком |
| FR-4 | Клиент может добавить товар из каталога в корзину | Обязательно | Нужно сделать | После добавления товар виден в корзине клиента с нужным количеством |
| FR-5 | Клиент может оформить заказ готовой мебели из корзины | Обязательно | Нужно сделать | После оформления появляется заказ со статусом "новый" со всеми позициями из корзины, корзина очищается |
| FR-6 | Клиент может оставить заявку на изготовление мебели по своим параметрам | Обязательно | Нужно сделать | После отправки параметров (размеры, описание) создаётся заявка со статусом "ожидает обработки" |
| FR-7 | Клиент может посмотреть статус своих заказов и заявок | Желательно | Нужно сделать | GET /orders отдаёт список заказов клиента с текущим статусом каждого |
| FR-8 | Менеджер может посмотреть список всех заказов и заявок | Обязательно | Нужно сделать | GET /manager/orders отдаёт все заказы и заявки со статусами |
| FR-9 | Менеджер может обработать заявку: уточнить параметры и посчитать стоимость | Обязательно | Нужно сделать | После обработки у заявки появляется стоимость и статус "подтверждена" или "отклонена" |
| FR-10 | Менеджер может поменять статус заказа | Обязательно | Нужно сделать | После смены статус обновляется и клиент видит новый статус у себя |

Ограничения (NFR):

| № | Ограничение |
|---|---|
| NFR-1 | Любой запрос к API обрабатывается не дольше 2 секунд при нормальной нагрузке (до 50 одновременных запросов) |
| NFR-2 | Пароли хранятся только в хэшированном виде (bcrypt), в открытом виде пароль не возвращается нигде и не пишется в логи |
| NFR-3 | Приложение запускается в Docker на Linux и Windows без доп. настройки, кроме переменных окружения для подключения к БД |
| NFR-4 | Все данные хранятся в PostgreSQL, напрямую к базе кроме backend никто не подключается |
| NFR-5 | Стек обязателен: Python 3.11, FastAPI, SQLAlchemy, Alembic. Менять на другой язык/стек нельзя |

### US-1. Регистрация и вход

Я как неавторизованный пользователь имею email и пароль, делаю: сначала `POST /auth/register` с этими данными, потом `POST /auth/login`. Получаю токен доступа и дальше хожу под клиентом.

Вход: email, пароль.
Выход: токен доступа, в базе появляется пользователь с ролью "клиент".

### US-2. Просмотр каталога

Я как клиент делаю `GET /products`, получаю список товаров с ценами и остатками.

Вход: без параметров (можно фильтр по категории).
Выход: список товаров.

### US-3. Добавление товара в корзину

Я как клиент знаю id товара из каталога, делаю `POST /cart/items` с product_id и количеством, получаю обновлённую корзину.

Вход: product_id, qty.
Выход: содержимое корзины с добавленным товаром.

### US-4. Оформление заказа готовой мебели (пример)

Я как клиент, у меня в корзине что-то лежит, делаю `POST /orders` (без тела, заказ собирается из текущей корзины), получаю созданный заказ.

Пример:
- Вход: в корзине `{"product_id": 12, "qty": 1}` (товар "Стол обеденный", цена 15000, в наличии 3 шт).
- Запрос: `POST /orders`.
- Выход: `201 Created`, `{"order_id": 501, "status": "new", "items": [{"product_id": 12, "qty": 1}], "total": 15000}`. Корзина после этого пустая.

Ошибка: если корзина пустая, `POST /orders` вернёт `400 Bad Request` с `{"error": "корзина пуста"}`, заказ не создастся, корзина не изменится.

Диаграмма: [sequence-order-success.mmd](diagrams/sequence-order-success.mmd).

### US-5. Создание заявки на индивидуальную мебель (пример)

Я как клиент знаю, какую мебель хочу, делаю `POST /custom-requests` с описанием и размерами, получаю заявку.

Пример:
- Вход: `{"description": "Шкаф-купе в прихожую", "width_cm": 180, "height_cm": 240}`.
- Запрос: `POST /custom-requests`.
- Выход: `201 Created`, `{"request_id": 77, "status": "pending_review"}`.

(Успешная диаграмма последовательности тут похожа на US-4, поэтому отдельно не рисовал - подробно показан именно вариант с ошибкой, US-6.)

### US-6. Заявка с неверными данными (ошибка, пример)

Я как клиент ввожу параметры неправильно, делаю `POST /custom-requests` с нечисловой шириной, получаю ошибку.

Пример:
- Вход: `{"description": "Шкаф", "width_cm": "широкий", "height_cm": 80}`.
- Запрос: `POST /custom-requests`.
- Выход: `400 Bad Request`, `{"error": "width_cm должен быть числом"}`. Заявка не создаётся, в базе ничего не появляется. По аналогии с примером из лекции: `GET /fib/str` должен вернуть 400, а не список чисел.

Диаграмма: [sequence-custom-request-error.mmd](diagrams/sequence-custom-request-error.mmd).

### US-7. Просмотр статуса своих заказов

Я как клиент авторизован (есть токен), делаю `GET /orders`, получаю список своих заказов и заявок с текущими статусами.

Вход: токен доступа.
Выход: список заказов/заявок, в каждом id и status.

### US-8. Менеджер смотрит список заказов и заявок

Я как менеджер делаю `GET /manager/orders`, получаю список всех заказов и заявок клиентов.

Вход: токен доступа менеджера.
Выход: список всех заказов и заявок с данными клиента и статусом.

### US-9. Менеджер обрабатывает заявку

Я как менеджер вижу заявку клиента со статусом "ожидает обработки", делаю `PATCH /manager/custom-requests/{id}` с уточнёнными параметрами и стоимостью, получаю обновлённую заявку со статусом "подтверждена" или "отклонена".

Вход: request_id, стоимость, решение (подтвердить/отклонить).
Выход: обновлённая заявка, при подтверждении создаётся заказ.

### US-10. Менеджер меняет статус заказа

Я как менеджер вижу заказ в статусе "новый" или "в работе", делаю `PATCH /manager/orders/{id}` с новым статусом, получаю обновлённый заказ.

Вход: order_id, новый статус.
Выход: заказ с новым статусом, клиент это видит в US-7.
